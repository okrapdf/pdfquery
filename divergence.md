1. No `pdfquery(fn)` ready-callback — use `pdfquery(doc).on('load', fn)`. (PDF trees do not have a DOM-ready lifecycle.)
2. No bubbling, capture, or delegation. (Events are a direct node-indexed broker, not a DOM propagation model.)
3. No auto-bridge to DOM-native events. (pdfquery's event plane is separate from browser UI events.)
4. No CSS selector engine. (Users bring selected object-shaped nodes from their own tree/index.)
5. No traversal methods (.find, .parent, .children, .closest, .siblings, .next, .prev). (pdfquery does not construct or own tree topology.)
6. No mutation methods (.append, .prepend, .remove, .clone, .replaceWith). (Tree mutation belongs to the caller's document model.)
7. No content-access methods (.attr, .text, .html, .val, .data, .prop). (PDF node schemas vary by parser/provider.)
8. No style methods (.css, .addClass, etc). (PDF styling is not a universal mutable DOM abstraction.)
9. `this` inside handlers NOT bound — handlers receive `PdfEvent<T>`. (Typed event objects are explicit and portable.)
10. `.each` does NOT support `return false` to break. (Iteration is intentionally simple and predictable.)
11. `.map` returns native array `U[]`, not Collection. (Mapping can produce arbitrary values, not only nodes.)
12. `pdfquery(primitive)` throws — WeakMap keys must be objects. (Event storage is WeakMap-backed.)
13. `pdfquery(fn)` throws with helpful message. (The old ready-callback shape is a migration hazard.)
